# CLAUDE.md — TAS-UP-4x-TouchRGB

## Project Overview

KNX home automation 4-channel capacitive touch panel firmware with RGB LED feedback.
MCU is RP2040 (dual-core ARM M0+) with 16MB flash, built with PlatformIO (Arduino framework).

## Build & Upload Commands

All commands run from the project root directory.
PlatformIO CLI is NOT in PATH — always use the full path.
Use `$USERPROFILE` (bash) or `%USERPROFILE%` (CMD) or `$env:USERPROFILE` (PowerShell) depending on the shell.
Claude Code uses bash — so use `$USERPROFILE` syntax here.

### PlatformIO (compile + upload)

```bash
# Build and upload (development, USB/picotool via COM3)
"$USERPROFILE/.platformio/penv/Scripts/platformio.exe" run -e develop_TAS_USB -t upload

# Build only (no upload)
"$USERPROFILE/.platformio/penv/Scripts/platformio.exe" run -e develop_TAS_USB

# Build and upload via J-Link
"$USERPROFILE/.platformio/penv/Scripts/platformio.exe" run -e develop_TAS_JLINK -t upload

# Release build (no upload target configured by default)
"$USERPROFILE/.platformio/penv/Scripts/platformio.exe" run -e release_TAS
```

### OpenKNXproducer (generate knxprod + knxprod.h)

Must run "Gen. Dependencies.txt" first, then the producer.
Use PowerShell with single-quoted `-Command` strings so `$env:USERPROFILE` expands in PowerShell, not bash.

```bash
# Step 1: Generate Dependencies.txt
powershell -ExecutionPolicy Bypass -Command "& './lib/OGM-Common/scripts/setup/reusable/Build-Dependencies.ps1'"

# Step 2: Run OpenKNXproducer (Dev)
powershell -ExecutionPolicy Bypass -Command '& (Join-Path $env:USERPROFILE "bin/OpenKNXproducer.exe") create --Debug -h include/knxprod.h src/TAS-UP-4x-TouchRGB.xml'

# Step 2 (alternative): Run OpenKNXproducer (Release)
powershell -ExecutionPolicy Bypass -Command '& (Join-Path $env:USERPROFILE "bin/OpenKNXproducer.exe") create --Debug -h include/knxprod.h src/TAS-UP-4x-TouchRGB-Release.xml'
```

### Build Release Package

```bash
powershell -ExecutionPolicy Bypass -Command "& './scripts/Build-Release.ps1' Release"
```

## Architecture

- **OpenKNX::Module pattern**: all modules override `setup()`, `loop()`, `processInputKo()`.
- **Dual-core**: Core 0 runs KNX stack + module logic, Core 1 runs LED refresh (50 FPS) + sensor I2C reads.
- **Module registration order** in main.cpp: Logic(1), THPSensor(2), VirtualButton(3), FileTransfer(9), TDD_Module(43).
- **KO number ranges**: THP 20-39, Logic 280-309, VirtualButton 380-455, TDD 630-650.

## Hardware

- **MCU**: RP2040, 16MB flash, dual-core ARM M0+
- **KNX**: NCN5120 transceiver on UART Serial1 (GPIO 0/1)
- **Touch**: CAP1188 on I2C (GPIO 16/17), 4 channels, threshold 100
- **LEDs**: SK6812 (GRB) on GPIO 18, 3 groups (1+40+1 LEDs), 50 FPS
- **Prog LED/Button**: GPIO 6 / GPIO 7

## OpenKNXproducer XML Structure

OpenKNXproducer takes a set of XML files as input and generates:
1. A `.knxprod` file (KNX product database for ETS configuration software)
2. `include/knxprod.h` — C++ header with `#define` macros for all parameters and KO accessors

### XML File Hierarchy

```
src/TAS-UP-4x-TouchRGB.xml          ← MAIN INPUT FILE (entry point for OpenKNXproducer)
  ├── src/TAS-UP-4x-TouchRGB.share.xml   ← App-specific module definition (TTD)
  ├── lib/OGM-Common/src/Common.share.xml              ← BASE module (shared)
  ├── lib/OFM-ConfigTransfer/src/ConfigTransfer.share.xml
  ├── lib/OFM-THPSensorModule/src/THPSensor.share.xml + .templ.xml
  ├── lib/OFM-VirtualButton/src/VirtualButton.share.xml + .templ.xml
  └── lib/OFM-LogicModule/src/Logikmodul.share.xml + .templ.xml

src/TAS-UP-4x-TouchRGB.debug.xml    ← AUTO-GENERATED expanded output (DO NOT edit or use as input)
src/TAS-UP-4x-TouchRGB.appl.debug.xml ← AUTO-GENERATED intermediate (DO NOT edit or use as input)
```

**The `.debug.xml` and `.appl.debug.xml` files are auto-generated by OpenKNXproducer for debugging purposes only. They are NOT input files — never edit them and never use them as source. They are regenerated on every producer run.**

### Main XML File (`TAS-UP-4x-TouchRGB.xml`)

This is the entry point. It contains:

- **`<op:ETS>`** — Product metadata (OpenKnxId, ApplicationNumber, version, product name, serial number)
- **`<op:define>`** — Module declarations. Each one registers a module with:
  - `prefix` — Short prefix used in generated `#define` names (e.g. `TTD`, `THP`, `LOG`, `BTN`)
  - `ModuleType` — Numeric module type identifier
  - `share` — Path to the module's `.share.xml` file
  - `template` — (optional) Path to the `.templ.xml` file for multi-channel modules
  - `NumChannels` — (optional) How many channel instances to create from the template
  - `KoOffset` — (optional) Base KO number for templated (multi-channel) modules
  - `KoSingleOffset` — (optional) Base KO number for single-instance modules (like TTD uses 630)
- **`<op:verify>`** — Version checks against `library.json` of each dependency
- **`<generate/>`** — Triggers the OpenKNXproducer to assemble the final output

Example module declaration:
```xml
<!-- Single-instance module (no template, no channels) -->
<op:define prefix="TTD" ModuleType="43" share="TAS-UP-4x-TouchRGB.share.xml" KoSingleOffset="630"/>

<!-- Multi-channel module (with template) -->
<op:define prefix="BTN" ModuleType="30" share=".../VirtualButton.share.xml"
          template=".../VirtualButton.templ.xml" NumChannels="16" KoOffset="380">
  <op:verify File=".../library.json" ModuleVersion="0.5"/>
</op:define>
```

### Share XML Files (`.share.xml`)

These define a module's ETS-visible content. Structure follows standard KNX XML schema with OpenKNX extensions:

1. **`<ParameterTypes>`** — Data type definitions for parameters
   - `TypeRestriction` with `<Enumeration>` — Dropdown/enum values (e.g. LED colors as RGB565)
   - `TypeNumber` — Numeric input (with `SizeInBit`, `minInclusive`, `maxInclusive`)
   - `TypeText` — Text input (with `SizeInBit`)
   - `TypePicture` — Image display (reference to a Baggage file)

2. **`<Parameters>`** — Parameter definitions with memory layout
   - `Name` — Parameter name (used in generated `ParamXXX_Name` macros in knxprod.h)
   - `ParameterType` — References a type from ParameterTypes
   - `Value` — Default value
   - `<Memory>` — Memory offset within the module's segment (`Offset` in bytes, `BitOffset` for sub-byte)

3. **`<ParameterRefs>`** — Reference layer (required by KNX spec, mirrors each Parameter)

4. **`<ComObjectTable>`** — Communication Objects (KOs) definition
   - `Name` — KO name (used in generated `KoXXX_Name` macros)
   - `Number` — Relative KO number within the module
   - `ObjectSize` — Data size (`1 Bit`, `1 Byte`, `3 Bytes`, etc.)
   - `DatapointType` — KNX DPT (e.g. `DPST-1-1` for switch, `DPST-232-600` for RGB color)
   - Flags: `ReadFlag`, `WriteFlag`, `CommunicationFlag`, `TransmitFlag`, `UpdateFlag`

5. **`<ComObjectRefs>`** — Reference layer for KOs (mirrors each ComObject)

6. **`<Dynamic>`** — ETS GUI layout
   - `<Channel>` — Tab/page in ETS
   - `<ParameterBlock>` — Groups parameters visually (with icon)
   - `<ParameterSeparator>` — Headlines, text, horizontal rules. Supports dynamic text via `TextParameterRefId` attribute with `{{0:default text}}` placeholder syntax.
   - `<ParameterRefRef>` — Places a parameter in the GUI
   - `<ComObjectRefRef>` — Makes a KO visible in the GUI
   - `<Button>` — Interactive button that calls a JavaScript function. Attributes: `EventHandler` (JS function name), `EventHandlerOnline` (`ConnectionOriented` for tunneling connection to device).

7. **`<Script>`** — ETS JavaScript inclusion (between `</ComObjectRefs>` and `</Static>`)
   - `<op:include href="filename.script.js" type="script" />` — Includes a JavaScript file
   - Scripts contain event handler functions called by `<Button>` elements
   - OpenKNXproducer validates that all `EventHandler` function names exist in the included scripts ("Integrity of script methods... OK")

8. **`<Baggages>`** — Embedded files (images, icons) shipped with the .knxprod

### Template XML Files (`.templ.xml`)

Used by multi-channel modules (THP, BTN, LOG). They define per-channel parameters and KOs that get replicated `NumChannels` times by OpenKNXproducer. The placeholder `%N%` is replaced with the channel index.

### ID Naming Convention (Placeholders)

- `%AID%` — Application ID (auto-generated)
- `%TT%` — Module tag (derived from prefix, e.g. `TTD`)
- `%MID%` — Memory segment ID
- `%ENID%` — Auto-generated enumeration ID
- `%PREFIX%` — Module prefix
- `%FILE-xxx%` — Baggage file reference

### Mapping to Firmware Code (knxprod.h)

OpenKNXproducer generates `#define` macros in `knxprod.h`:

| XML Element | Generated Macro Pattern | Example |
|---|---|---|
| Parameter `Name="LEDColor"` with prefix `TTD` | `ParamTTD_LEDColor` | Returns parameter value from memory |
| ComObject `Name="LEDColor"` with prefix `TTD` | `KoTTD_LEDColor` | Returns GroupObject reference |
| ComObject Number (absolute) | `TTD_KoLEDColor` | Absolute KO number (for switch/case) |

Absolute KO number calculation:
- **Single-instance modules**: `KoSingleOffset + Number` (TTD: 630 + 3 = 633)
- **Templated modules**: `KoOffset + channelIndex * KoBlockSize + Number`

### How to Add a New Parameter

1. Define a `<ParameterType>` in the share XML (or reuse an existing one)
2. Add a `<Parameter>` with a unique `Name`, the type reference, default `Value`, and `<Memory Offset="..."/>`
3. Add a `<ParameterRef>` mirroring it
4. Add a `<ParameterRefRef>` inside the appropriate `<ParameterBlock>` in `<Dynamic>` to make it visible in ETS
5. Re-run OpenKNXproducer to regenerate `knxprod.h`
6. Access in firmware via `ParamTTD_YourName`

### How to Add an ETS Script Button with FunctionProperty

This pattern allows ETS to communicate directly with the device via the KNX bus (e.g. for diagnostics).

**XML side (share.xml):**

1. Add a display-only `<Parameter>` with `Access="None"` and no `<Memory>` element (ETS-side only, no device memory)
2. Add a matching `<ParameterRef>`
3. Add a `<Script>` block with `<op:include href="YourFile.script.js" type="script" />` (between `</ComObjectRefs>` and `</Static>`)
4. In `<Dynamic>`, add:
   - A `<ParameterSeparator>` with `TextParameterRefId` for dynamic text display (`{{0:default}}` syntax)
   - A `<ParameterRefRef>` for the display parameter (needed so the script can write to it)
   - A `<Button>` with `EventHandler="functionName"` and `EventHandlerOnline="ConnectionOriented"`

**JavaScript side (.script.js):**

- Function signature: `function name(device, online, progress, context)`
- `online.connect()` / `online.disconnect()` — open/close tunneling connection
- `online.invokeFunctionProperty(objectIndex, propertyId, data)` — send command, get response
- `device.getParameterByName("PREFIX_Name").value = result` — write to display parameter

**Firmware side (C++):**

- Override `processFunctionProperty(objectIndex, propertyId, length, data, resultData, resultLength)` in your module
- Check `objectIndex` and `propertyId` to filter requests for your module
- Use `data[]` for command bytes, fill `resultData[]` with response, set `resultLength`
- Return `true` if handled, `false` to pass to next module

**FunctionProperty objectIndex assignment:**

Each module hardcodes a unique `objectIndex` (not auto-generated). The framework broadcasts every FunctionProperty call to all modules in a loop; the first to return `true` handles it. Current assignments:

| objectIndex | Module |
|---|---|
| 158 (0x9E) | OGM-Common (BASE) |
| 159 | OFM-FileTransferModule |
| 160 | OFM-LogicModule |
| 161 | TDD_Module |

Next free objectIndex: **162**. Within a module, use `propertyId` for different endpoints and `data[0]` for different commands.

### How to Add a New Communication Object (KO)

1. Add a `<ComObject>` in `<ComObjectTable>` with unique `Name`, `Number`, size, DPT, and flags
2. Add a `<ComObjectRef>` mirroring it
3. Add a `<ComObjectRefRef>` in the appropriate `<ParameterBlock>` in `<Dynamic>`
4. Re-run OpenKNXproducer to regenerate `knxprod.h`
5. Access in firmware: `KoTTD_YourName` (GroupObject) and `TTD_KoYourName` (absolute number for switch/case)

## Important Notes

- `include/knxprod.h` is auto-generated by OpenKNXproducer — never edit manually.
- `src/TAS-UP-4x-TouchRGB.debug.xml` and `.appl.debug.xml` are auto-generated debug outputs — never edit or use as input.
- After changing `src/TAS-UP-4x-TouchRGB.xml` or `.share.xml`, re-run OpenKNXproducer to regenerate.
- Core 1 loop1() calls module loop1() directly (not via openknx.loop1()) due to a CAP1188 timing issue.
- The `5000ms delay` in setup() is intentional — allows USB serial connection before boot messages.
